# Product Requirements Document - StockManagement

**Author:** Fujita_kenshirou
**Date:** 2026-03-03

## Executive Summary

StockManagement は、中長期保有を志向する個人投資家のための財務分析Webアプリケーションである。企業価値評価の基本理論に基づき理論株価を算出し、定量分析と定性分析を統合することで、投資家が自信を持って売買判断を行える環境を提供する。

対象ユーザーは、理論ベースの分析を自力で実践している（または実践したい）個人投資家である。現在このような投資家に、容易にデータ分析に使える形式で情報提供しているツールは少ない。そのため財務データの入力に膨大な手間がかかる状況である。それにより、本来注力すべき分析と判断に時間を割けていない。新NISA等で個人投資が広がる中、理論に基づくまっとうな分析ツールは少ない。有料ツールは有用だが投資リターンの削減につながり、無料ツールは痒い所に手が届く機能に乏しい。

StockManagement は、EDINET等の公式開示情報からの財務データ収集を段階的に自動化し、理論株価の算出、動的な投資ロースター管理、AI支援による定性分析を一体的に提供する。

### What Makes This Special

**透明性の原則**がすべてを貫く設計思想である。計算ロジック・データ判定の根拠・前提パラメータをすべて開示し、投資家が「なぜその数字になったか」を理解できる。本ツールは過程と根拠の透明性に徹底的にこだわる。

- **理論の民主化**: 企業価値評価理論を、誰でも無料で、中身を理解しながら使える
- **信念＋客観性の両立**: 投資家個人の「いい会社とは何か」という価値基準と、厳密な財務分析を独自に統合
- **定量＋定性の統合**: 決算指標（バックミラー）とAIによる事実整理（フロントガラス）を組み合わせ、過去だけでなく未来の見通しも判断材料にする
- **無料かつオープンソース志向**: ペイウォールなし。計算ロジックの完全な透明性

## Product Scope

### MVP — Minimum Viable Product

**Phase 1: 理論株価計算エンジン + 最低限のWebUI**
- 銘柄を選択して財務データを手動入力
- 理論株価、ROE / ROA / ROIC、自己資本比率、営業CF / 投資CF / FCF、PER / PBR を自動算出
- 選択した銘柄の理論株価・各指標を一覧表示
- 計算ロジックの閲覧機能（透明性の原則）
- パラメータは以下の3分類で管理する（詳細は計算ロジック棚卸し時に確定）：
  - **ユーザー調整可能**: 投資家の見立てが入る前提パラメータ（成長率、割引率等）
  - **自動算出**: 財務データから機械的に計算される指標（ROE、ROIC等）
  - **入力値**: 決算資料から取得する元データ（売上高、営業利益等）

**Phase 2: データ入力の効率化**
- EDINET等からの財務データ自動取得（主要項目）
- 自動判定が困難な項目は半自動（候補値提示 → ユーザー確認）
- データ判定ログの記録・表示

### Growth Features（Post-MVP）

**Phase 3: ロースター管理＋スクリーニング**
- スタメン／スーパーサブ／ベンチ／候補生／分析済み落第の分類・管理
- 分類変更の履歴と理由の記録
- 銘柄間比較ビュー、簡易スクリーニング機能

**Phase 4: 定性分析（AI支援）**
- ライト定性: 事業概要・セクター・主要事業の自動取得
- ディープ定性: IR資料からの事実整理（経営者の言行追跡、競争優位性の源泉特定）
- AIはスコアリングせず事実の提示に徹する

### Vision（Future）

**Phase 5: 教育コンテンツ / OSS・公開準備**
- 「なぜこの計算式で理論株価が出るのか」の理論解説
- ペルソナB（不安を抱える投資家）向け導入ガイド
- OSS公開 or 課金アプリとしてのリリース

**オプション（時期未定）**
- 過去データのインポート（CSV/スプレッドシート移行ツール）
- モバイル対応（レスポンシブUI）
- 国際市場対応

## User Journeys

### Journey 1: 決算シーズン — 保有銘柄の一斉アップデート（成功パス）

**藤田 — 金曜の夜、決算ラッシュの真っ只中**

四半期決算の発表が集中する2月。藤田のポートフォリオに含まれる30社以上の企業が次々と決算短信を開示している。以前はこの時期、仕事終わりの夜と週末をほぼすべてスプレッドシートへのデータ転記に費やしていた。面倒で後回しにした結果、データの入力ができていない企業も多数あった。

**Phase 1（手動入力）の場合:**
藤田はStockManagementを開き、決算短信を見ながら財務データを入力する。スプレッドシートとは違い、入力フォームが構造化されているため迷わない。入力が完了すると、理論株価・ROE・ROIC・FCF等の指標が即座に更新される。計算ロジックの閲覧ボタンを押せば、「なぜこの理論株価になったか」の数式と参照元がすべて見える。

**Phase 2（半自動取得）の場合:**
決算が開示されると、EDINETから主要な財務データが自動取得される。一部の項目（例：有利子負債に含める勘定科目の判定）はツールが候補値を提示し、藤田が確認・修正する。「この会社の"長期借入金"を有利子負債に含めた」という判定ログが残るため、次回以降は同じ判断を再利用できる。

**クライマックス:**
保有銘柄の理論株価一覧を眺めながら、ある銘柄の理論株価が市場価格を大幅に上回っていることに気づく。パラメータ（成長率・割引率）を保守的に調整しても、まだ割安と判定される。「これは買い増しのチャンスだ」と、根拠を持って判断できる。

**解決後の世界:**
決算シーズンが「データ入力地獄」から「分析と判断の季節」に変わる。空いた時間で、気になっていた新規銘柄の定性分析に着手できるようになった。

### Journey 2: 新規銘柄の発掘 — スクリーニングから投資判断まで（平時）

**藤田 — 休日の午後、新しい投資先を探す**

株探でざっくりスクリーニングをかけ、ROEやROICが高く時価総額が手頃な企業を数社ピックアップした。名前を聞いたことのない会社が混じっている。「どんな会社なんだろう」と興味を持つ。

**ライト定性（Phase 4 の機能。Phase 1 では手動）:**
まず事業領域を調べる。現段階では企業のIRページを見てざっくり把握する。「BtoB向けのニッチなソフトウェア会社か。面白そう」と判断し、定量分析に進めることにする。

**定量分析（Phase 1）:**
StockManagementに銘柄を追加し、直近3期分の財務データを入力する。理論株価が算出され、現在の市場価格と比較する。自己資本比率が高く、FCFも安定して黒字。ROICも水準以上。理論株価の半額程度の株価で、数値的にはあらゆる基準を満たしている。

**ディープ定性（Phase 4 の機能。Phase 1 では手動）:**
数値が良いからといって即決はしない。決算説明資料を読み、経営者の過去の発言と実績を照らし合わせる。競争優位性の源泉（スイッチングコストの高さ）を特定し、それが持続可能かを考える。現段階ではこのプロセスは手動だが、将来的にはAIが事実の整理を支援する。

**クライマックス:**
定量・定性の両面から「この会社はいい」と確信が持てた。ロースター（Phase 3 の機能）の「候補生」に追加し、次の決算で買い増し判断をする予定を立てる。

**解決後の世界:**
「スクリーニング → ライト定性 → 定量 → ディープ定性 → ロースター決定」の一連のフローが、ツールの中で（段階的に）完結するようになる。

### Journey 3: データ不整合への対処（エッジケース）

**藤田 — 理論株価の計算結果に違和感を覚える**

ある銘柄の理論株価を更新したところ、前期と比べて異常に大きな変動が出た。「こんなに変わるはずがない」と直感的に感じる。

**調査:**
計算ロジックの閲覧機能を使い、どの入力値がどの計算に影響しているかを確認する。すると、有利子負債の数値が前期と大きく異なっていることに気づく。決算短信を確認すると、今期から勘定科目の表記が変わっており（「長期借入金」→「社債及び長期借入金」）、入力値に誤りがあった。

**修正と学び:**
正しい値に修正し、理論株価が妥当な範囲に戻ることを確認する。Phase 2 以降では、このような勘定科目の変動はデータ判定ログに記録され、「前期と異なる勘定科目マッピングが検出されました」というアラートが出る設計にする。

**クライマックス:**
計算過程が透明だからこそ、違和感の原因を自力で特定・修正できた。ブラックボックスのツールでは「なぜ数値が変わったか」がわからず、結果を信用できなくなるところだった。

**解決後の世界:**
透明性の原則が、単なる理念ではなく実務上の安全弁として機能していることを実感する。

## Domain-Specific Requirements

### データ正確性

- **計算ロジックの正確性**: 理論株価の算出結果が既存スプレッドシートと一致することが最低条件。端数処理・単位（百万円/千円/円）・期ズレ（年度/四半期、連結/単体）の3つが主なズレ原因であり、テストで最初に固定する
- **財務データの整合性**: 入力値の妥当性チェック（例：自己資本比率が0〜100%の範囲か、売上高が負値でないか等）は最低限の入力バリデーションとして実装する

### EDINET API 利用（Phase 2）

- **利用規約への準拠**: EDINET APIの利用規約を遵守する。アクセス頻度の制限、データの二次利用条件を確認の上で設計する
- **XBRL タクソノミの不統一**: 企業ごとに勘定科目の表現が異なるため、勘定科目マッピングの仕組みとその判定ログが必須となる

### データプライバシー（OSS公開時）

- **個人の投資データ**: ポートフォリオ情報や売買判断は個人の金融情報にあたる。OSS公開時にはローカル保存 or ユーザー自身のDBインスタンスを前提とし、開発者側にユーザーデータが渡らない設計にする（具体的な基準は NFR9 を参照）
- **Phase 1（個人利用）**: 個人のSupabaseインスタンスに格納。セキュリティリスクは低い

### リスクと軽減策

| リスク | 影響 | 軽減策 |
|--------|------|--------|
| 計算ロジックの誤り | 誤った理論株価に基づく投資判断 | テストケースによる検証、計算過程の完全開示（ユーザー自身が検算可能） |
| EDINET データの不整合 | 誤った財務データの取り込み | 半自動確認フロー、判定ログ、前期比異常値アラート |
| 勘定科目マッピングの誤り | 有利子負債等の過大/過小評価 | マッピング判定の透明化、ユーザー確認ステップ |

### 免責事項

本ツールは投資助言を行うものではない。理論株価の算出結果およびすべての分析情報は参考値であり、最終的な投資判断はユーザー自身の責任において行うものとする。

## Web App Specific Requirements

### Project-Type Overview

Next.js (App Router) による SPA として構築する。個人投資家が決算シーズンおよび平時に利用する分析ツールであり、リアルタイム性は不要。Phase 1 は個人利用に特化し、OSS公開フェーズでパブリック向けの要件（SEO、アクセシビリティ等）を拡張する。

### Technical Architecture Considerations

- **レンダリング戦略**: クライアントサイドレンダリング（CSR）を基本とする。計算処理はクライアント or API Routes で実行。SSR/SSG は Phase 1 では不要
- **状態管理**: 銘柄一覧・財務データ・計算結果をクライアントで管理。Supabase をバックエンドDBとして利用
- **API設計**: Next.js API Routes で Supabase への CRUD 操作を提供。外部API（EDINET）連携は Phase 2 で追加
- **認証**: Phase 1 は個人利用のため最小限（Supabase Auth のメール認証程度）。マルチユーザー対応は OSS 公開時に検討

### Browser Support

- **対象**: Chrome, Firefox, Safari, Edge の最新2バージョン
- **非対象**: IE, モバイルブラウザ（Phase 1）
- **レスポンシブ対応**: Phase 1 はデスクトップファースト。モバイル対応はオプション（時期未定）

### Performance Targets

具体的なパフォーマンス基準は Non-Functional Requirements（NFR1〜NFR5）を参照。

### Implementation Considerations

- **TypeScript**: 型安全性を重視。計算ロジックの信頼性確保のため
- **テスト**: 計算ロジックに対するユニットテストを最優先。E2Eテストは後回し
- **デプロイ**: Vercel（無料枠）。CI/CD は GitHub Actions で自動化
- **コスト制約**: Supabase 無料枠（500MB DB、50,000 行）+ Vercel 無料枠。月額 ¥0 を維持
- **データモデル方針**: Phase 1 は財務データをワイドテーブル（1期=1行、指標を列で保持）とする。行数制約（50,000行）下で銘柄数を最大化するため。詳細はアーキテクチャ設計時に確定する

## Project Scoping & Phased Development

Product Scope セクションで定義したフェーズ構成に対する戦略的根拠とリスク分析を以下に記述する。

### MVP Strategy & Philosophy

**MVPアプローチ: Problem-Solving MVP（課題解決型）**

StockManagement のMVPは「最小限の機能で最大の課題を解決する」アプローチを取る。開発者自身が最初のユーザーであるため、市場検証やユーザー獲得の前に「自分の課題を解決できるか」を検証する。

- **フィードバックループ**: 開発者 = ユーザーのため、即座に改善サイクルを回せる
- **品質基準**: 「スプレッドシートの代わりに使えるか」が唯一の判定基準
- **リソース**: 1人開発（週7-8時間）。技術スタック学習を含む

### MVP Feature Set（Phase 1）

**支援するコアジャーニー:**
- Journey 1（決算シーズン）の手動入力パス
- Journey 2（新規銘柄発掘）の定量分析部分
- Journey 3（データ不整合）の計算ロジック閲覧による自己解決

**Must-Have:**
- 銘柄の登録・管理（CRUD）
- 財務データの手動入力フォーム
- 理論株価 + 主要指標の自動算出
- 計算ロジックの閲覧機能
- ユーザー調整可能パラメータ（成長率、割引率等）
- 銘柄一覧での理論株価・指標表示

**明示的に Phase 1 から除外:**
- データの自動取得（→ Phase 2）
- ロースター管理（→ Phase 3）
- 定性分析（→ Phase 4）
- 教育コンテンツ（→ Phase 5）
- スクリーニング機能（→ Phase 3）
- モバイル対応、過去データインポート

### Post-MVP Features

**Phase 2（Growth — データ効率化）:**
Phase 1 のジャーニーを「手動」から「半自動」に進化させる。ユーザー価値: データ入力時間の50%以上削減。

**Phase 3-4（Expansion — 分析の高度化）:**
銘柄選定の5ステップフロー全体をツール内で完結させる。ユーザー価値: スクリーニングから投資判断までのワンストップ化。

**Phase 5（Vision — 公開・教育）:**
個人ツールから公共財へ。ユーザー価値: 投資理論の民主化。

### Risk Mitigation Strategy

| カテゴリ | リスク | 軽減策 |
|---------|--------|--------|
| **技術** | TypeScript/Next.js の学習コスト | Phase 1 は最小構成。学びながら作る前提でスコープを絞る |
| **技術** | 計算ロジックの移植精度 | テストファースト（1銘柄×3期のテストケースを最初に作成） |
| **技術** | Supabase 無料枠の制限 | 50銘柄×数年分のデータ量を事前に見積もり。不足時はセルフホスト検討 |
| **リソース** | 1人開発で週7-8時間 | マイルストーンは目安。遅延OK。スコープ削減で対応 |
| **リソース** | モチベーション維持 | 自分が使うツールを作るため、実用性がモチベーションになる |
| **市場** | OSS公開後のユーザー獲得 | Phase 1-4 は自分用。市場リスクはPhase 5 で初めて発生 |

## Functional Requirements

### Phase 1 スコープ早見表

- **Phase 1 対象**: FR1-4, FR8-12, FR18-23, FR27-28, FR34-35
- **Phase 2**: FR13-17, FR29-30
- **Phase 3**: FR5-6, FR24-26
- **Phase 4**: FR7, FR31-33

### 銘柄管理

- **FR1**: ユーザーは銘柄を新規登録できる（銘柄コード、企業名、市場、業種、事業セグメント）
- **FR2**: ユーザーは登録済み銘柄の情報を編集・削除できる
- **FR3**: ユーザーは登録済み銘柄の一覧を閲覧できる
- **FR4**: ユーザーは銘柄一覧で各銘柄の理論株価・主要指標を一目で確認できる
- **FR5**: ユーザーは銘柄をロースターカテゴリ（スタメン／スーパーサブ／ベンチ／候補生／分析済み落第）に分類できる *[Phase 3]*
- **FR6**: ユーザーはロースター分類の変更履歴と理由を記録・閲覧できる *[Phase 3]*
- **FR7**: ユーザーはAIによる当該銘柄の調査結果（定性評価のための事実情報）を取得・閲覧できる *[Phase 4]*

### 財務データ管理

- **FR8**: ユーザーは銘柄ごとに四半期・年度の財務データを手動入力できる（売上高、営業利益、税引後利益、総資産、自己資本、有利子負債、営業CF、投資CF、普通株式数、支払利息、現在株価 等）
- **FR9**: ユーザーは入力済み財務データを修正できる
- **FR10**: ユーザーは銘柄ごとの財務データの推移（複数期分）を閲覧できる
- **FR11**: システムは入力値に対して基本的な妥当性チェックを行う（負値チェック、範囲チェック等）
- **FR12**: ユーザーは財務データの期間属性（年度/四半期、連結/単体）を指定できる
- **FR13**: システムはEDINET等から主要な財務データを自動取得できる *[Phase 2]*
- **FR14**: システムは自動判定が困難な項目について候補値を提示し、ユーザーが確認・修正できる *[Phase 2]*
- **FR15**: システムはデータ判定の過程をログとして記録・表示できる *[Phase 2]*
- **FR16**: システムは過去の勘定科目マッピング判定を再利用できる *[Phase 2]*
- **FR17**: システムは前期と異なる勘定科目マッピングを検出した場合にアラートを出せる *[Phase 2]*

### 計算エンジン — 前提パラメータ（ユーザー設定）

- **FR18**: ユーザーは銘柄ごとに以下の前提パラメータを設定・調整できる：
  - **基本パラメータ（Phase 1 UI露出）**: r（割引率）/ g（永久成長率）/ 実効税率
  - **高度設定（Phase 1 ではデフォルト値で固定、Phase 2 以降でUI露出）**: β値 / 支払利息率 / 負債調達コスト / 資本調達コスト / 理論割引率
- **FR19**: システムはパラメータのデフォルト値を提供し、ユーザーはそのデフォルト値と根拠を確認できる
- **FR20**: システムはパラメータ変更時に関連するすべての指標を即座に再計算できる

### 計算エンジン — 自動算出指標

- **FR21**: システムは以下の指標を財務データとパラメータから自動算出できる：
  - 自己資本比率 / 純利益率 / 売上営業利益率
  - 前年比売上成長率 / 前年比利益成長率
  - 営業CF / 投資CF / FCF
  - ROE / ROA / ROIC / 移動平均ROIC
  - PER / PBR / EPS
  - 現状事業価値 / 現状資産価値
  - 現状理論株価 / 成長込理論株価
  - 理論PER / 理論時価総額 / 5年後理論時価総額 / 6年目当期純利益
  - 安全域（現状）/ 安全域（成長込）/ 安全率（現状）/ 安全率（成長込）
  - 理想購入株価（対現状）/ 理想購入株価（対成長）

### 計算エンジン — 銘柄詳細ビュー

- **FR22**: ユーザーは銘柄ごとに以下の情報を一覧で閲覧できる：
  - r / g / 理論PER / 最新当期純利益 / 6年目当期純利益
  - 5年後理論時価総額 / 現状時価総額 / 株主資本 / 理論時価総額 / 普通株式数
  - 現状理論株価 / 成長込理論株価 / 現状株価
  - 理想購入株価（対現状）/ 理想購入株価（対成長）
  - 現状株価安全域 / 成長込株価安全域
  - 安全率（現状）/ 安全率（成長込）
  - EPS / PER
- **FR23**: システムは理論株価と現在の市場価格を比較表示できる。現在株価が未入力の場合、比較表示は非活性とする

### 銘柄比較ビュー

- **FR24**: ユーザーは複数銘柄を以下の項目で横並びに比較できる *[Phase 3]*：
  - 社名 / 事業セグメント
  - 安定性（5段階評価）/ 成長性（5段階評価）/ 資本効率（5段階評価）/ 競争優位（5段階評価）/ 割安度（5段階評価）
  - 現状理論株価 / 成長込理論株価 / 現在株価
  - 理想買入額 / 理想売却額
  - 安全域（現状）/ 安全率（現状）/ 安全域（成長込）/ 安全率（成長込）
  - 購入優先順
  - 最新評価更新日時
  - 総合評価（ユーザーがコメント入力可能）
- **FR25**: ユーザーは各銘柄の5段階評価（安定性・成長性・資本効率・競争優位・割安度）を手動で設定できる *[Phase 3]*
- **FR26**: ユーザーは購入優先順を手動で設定できる *[Phase 3]*

### 透明性・計算ロジック閲覧

- **FR27**: ユーザーはすべての計算ロジック（数式、理論的根拠）を閲覧できる
- **FR28**: ユーザーは各指標の算出に使用された入力値と数式の参照関係を追跡できる

**Phase 1 における透明性の最低表示項目（各指標に対して）:**
- 数式（文字列表現）
- 使用した入力値（期・連結/単体・単位付き）
- 端数処理ルール（四捨五入/切捨て、桁数）
- 計算バージョン（calc_version）
- 入力→指標の依存関係はテーブル形式の参照一覧とする（グラフ可視化は Phase 2 以降で検討）

### データ取得自動化

- **FR29**: システムはEDINET APIと連携して有価証券報告書（XBRL）の主要財務項目を取得できる *[Phase 2]*。決算短信は企業ごとに粒度が異なるため Phase 2 以降で追加検討する
- **FR30**: システムはXBRLデータから必要な財務項目を抽出・マッピングできる *[Phase 2]*

### 定性分析

- **FR31**: システムは銘柄の事業概要・セクター・主要事業を表示できる *[Phase 4]*
- **FR32**: システムはIR資料から事実を整理して提示できる（経営者の発言と実績の照合、競争優位性の源泉特定等） *[Phase 4]*
- **FR33**: システムは定性分析において事実の提示に徹し、スコアリングは行わない *[Phase 4]*

### 認証・アカウント

- **FR34**: ユーザーはアカウントを作成してログインできる
- **FR35**: ユーザーのデータはアカウントに紐づいて保存される

## Non-Functional Requirements

### パフォーマンス

- **NFR1**: 1銘柄あたりの理論株価算出は3秒以内に完了すること
- **NFR2**: 50銘柄以上の一覧表示は1秒以内にレンダリングされること
- **NFR3**: 初回ページロードは3秒以内に完了すること（Vercel CDN利用前提）
- **NFR4**: パラメータ（割引率・成長率等）の変更時、関連指標の再計算が1秒以内に画面に反映されること
- **NFR5**: EDINET データ取得はバックグラウンド処理とし、UIをブロックしないこと *[Phase 2]*

### セキュリティ

- **NFR6**: すべての通信はHTTPS（TLS 1.2以上）で暗号化されること
- **NFR7**: Supabase の Row Level Security（RLS）を Phase 1 から有効にし、認証済みユーザーが自身のデータのみにアクセスできること
- **NFR8**: 認証トークンはセキュアに管理し、クライアントサイドに機密情報を露出しないこと
- **NFR9**: OSS公開時、ユーザーのポートフォリオ・投資判断データが開発者側に一切渡らないアーキテクチャとすること（ローカル保存 or ユーザー自身のDBインスタンス）

### アクセシビリティ

- **NFR10**: Phase 1 から WCAG 2.1 Level AA に準拠すること
- **NFR11**: すべてのインタラクティブ要素がキーボードのみで操作可能であること（Tab移動、Enter/Spaceでの操作、Escでのキャンセル）
- **NFR12**: スクリーンリーダー（VoiceOver, NVDA等）で全機能が利用可能であること。適切なARIAラベル・ランドマーク・ライブリージョンを実装すること
- **NFR13**: 主要操作に対するキーボードショートカットを提供し、スクリーンリーダーユーザーが効率的に操作できること
- **NFR14**: 色のみに依存する情報伝達を行わないこと。テキストラベル・パターン・アイコン等を併用すること
- **NFR15**: テキストと背景のコントラスト比は WCAG AA 基準（4.5:1以上、大文字は3:1以上）を満たすこと

### インテグレーション

- **NFR16**: EDINET API との連携において、API利用規約で定められたアクセス頻度制限を遵守すること *[Phase 2]*
- **NFR17**: 外部API（EDINET、AI API）の障害・タイムアウト時にユーザーに明確なエラーメッセージを表示し、手動入力へのフォールバックを提供すること
- **NFR18**: 外部APIリクエストのタイムアウトは30秒以内とし、リトライは最大3回までとすること

### 信頼性

- **NFR19**: Supabase のデータベースバックアップ（自動）を有効にし、データ消失リスクに備えること
- **NFR20**: 計算エンジンのロジック変更時に既存データの整合性が保たれること（マイグレーション戦略の明確化）
- **NFR21**: 障害発生時のデータ復旧手順をドキュメント化すること
